## Findings

- Stock Spruce SDL and Mali libraries can create an accelerated ES2 context.
- A logical 640x480 RGBA render target is supported.
- The mali-fbdev drawable remains the physical portrait geometry, 480x640.
  NextUI therefore needs an explicit rotated presentation pass.

  The presentation pass must pre-rotate logical output 90 degrees
  counter-clockwise.
- The ES2 counter-rotated presentation test produced the expected physical
  quadrant layout. The logical-FBO presentation strategy is validated.

## MinArch and Gambatte smoke test

The first MinArch hardware run reached SDL/GLES initialization but stopped
cleanly because the initial alpha package omitted its three built-in shaders.
The package now installs the GLES2-compatible `default.glsl`, `overlay.glsl`,
and `noshader.glsl` files.

The repeated run used Spruce's `gambatte_libretro.so` and a zipped Game Boy
ROM. It remained alive for the bounded test window and then restored Spruce.
The runtime log confirmed:

- a 480x640 Mali window and 640x480 A30 gameplay framebuffer;
- successful compilation/linking of all three built-in GLES2 shaders;
- Gambatte `v0.5.0-netlink 0092232` core and zipped-ROM loading;
- RGB565 core output at 160x144 and 59.7275 fps;
- ALSA output through `sndcodec` at 32768 Hz; and
- ARM NEON pixel conversion.

The hardware tester played a short Tetris level and confirmed correct visible
gameplay, sound, D-pad input, and the face buttons exercised during play.
The analog stick, L1/L2/R1/R2, and MinArch Menu behavior were not exercised in
this run.

A direct repeat launch exposed a test-harness lifecycle issue: suspending
Spruce `MainUI` can leave its `/dev/snd/pcmC0D0p` descriptor open, causing
MinArch's ALSA initialization to block. The blocked run took 60.373 seconds to
initialize and only displayed a frame as its timeout expired.

The next run used Spruce's canonical `/tmp/cmd_to_run.sh` handoff instead.
`MainUI` exited and released ALSA before `principal.sh` launched MinArch;
startup returned to 518 ms. MinArch recorded two overlay updates during the
test, and Spruce started a fresh `MainUI` after the bounded run. Temporary
hardware tests should use this canonical handoff rather than `SIGSTOP` on
Spruce's frontend.

The hardware tester confirmed that Menu paused the game, displayed MinArch's
menu correctly, and resumed gameplay quickly and easily. The analog stick did
not move Tetris; this was subsequently traced to the unavailable Spruce UART
alias rather than a mapping preference. L1/L2/R1/R2 had no observable effect,
as expected for a Game Boy title, so shoulder input remained unvalidated
pending a GBA or SNES test.

The first gpSP/Mario Kart GBA run showed why analog was absent: Spruce removes
its temporary `/dev/ttyS0` symlink when PyUI exits. NextUI now opens the
physical `/dev/ttyS2` UART first and treats `/dev/ttyS0` only as a compatibility
fallback. The repeated run logged a successful `/dev/ttyS2` open and started
in 463 ms.

The first GBA run also exposed a missing `/mnt/SDCARD/Saves/GBA` directory.
MinArch now creates its resolved per-core save directory along with config and
state directories. The repeated run wrote a 131072-byte Mario Kart `.sav`
without an SRAM error.

During the corrected Mario Kart run, L and R both produced their expected GBA
actions and the thumbstick steered correctly through MinArch's digital-input
mapping. The hardware tester reported all tested controls green.

A subsequent two-minute Mario Kart run exercised MinArch's in-game Save and
Load entries. Saving a state, advancing gameplay, and loading the state
returned to the saved moment correctly.

One Spruce-to-NextUI handoff began at a quiet output level, after which the
first Volume Up press caused a much larger-than-expected increase. Spruce and
NextUI maintain separate persisted volume values while sharing the A30's
`Soft Volume Master` control, so this result is not yet attributed to the
standalone port. Re-test the full 0–20 volume range after cold-booting a pure
NextUI installation.

## Native NextUI cores

The new `my282` core target produced the complete initial MinUI-compatible
set using the A30 toolchain:

- FCEUmm
- Gambatte
- gpSP
- PicoDrive
- Snes9x 2005
- PCSX-ReARMed

All six outputs are 32-bit ARMv7 EABI5 hard-float shared objects and export
the expected libretro lifecycle API. gpSP, PicoDrive, and PCSX-ReARMed carry
NEON attributes; gpSP and PCSX-ReARMed use their ARM dynarecs. Their dynamic
dependencies are limited to the standard C/C++ runtime, math, pthread, and
`libdl`.

PicoDrive and PCSX-ReARMed vendor 7-Zip 24.05 code which assumes ARMv8 crypto
`HWCAP2` definitions for all 32-bit ARM Linux builds. The A30 platform patches
retain runtime NEON detection but correctly report CRC32/SHA/AES acceleration
as unavailable on its Cortex-A7. Both cores also require uppercase
`PLATFORM=libretro` for their internal frontend object selection while the
outer build continues to use lowercase `platform=my282`.

The native gpSP core—not Spruce's RetroArch copy—was staged under
`.system/my282/cores` and launched with Mario Kart. It identified itself as
`gpSP v1.1.0-5b6e751`, opened `/dev/ttyS2`, initialized in 633 ms, and remained
in the emulation loop for the bounded test with no logged errors. The hardware
tester played briefly and reported normal gameplay with no video, audio, or
control complaints. Menu and state operations were not repeated because those
MinArch paths were already validated in the preceding GBA test.

The initial native Snes9x 2005 Plus core was then launched with zipped Super Mario
World through the canonical Spruce command handoff. It identified itself as
`Snes9x 2005 Plus v1.36-deb49d8`, loaded RGB565 output at 256x224 and
59.922743 fps, opened ALSA at 32040 Hz, enabled MinArch's ARM NEON conversion,
and entered gameplay in 531 ms. The bounded run reached SRAM write and MinArch
overlay-update paths. ALSA reported several recoverable underruns; visible
gameplay, perceived audio continuity, controls, Menu behavior, and state
operations await the hardware tester's report.

The hardware tester reported that Super Mario World was visibly laggy and
showed tearing. L/R had no observed effect in the tested section, though that
game does not make their camera-scroll behavior obvious everywhere. One
save/load-state round trip succeeded. This is not the A30 stock firmware's
well-known RetroArch `Normal2x` regression: MinArch has no RetroArch CPU-filter
stage and the log reported zero active shaders. The first native build did,
however, force Snes9x 2005 Plus's more expensive Blargg APU, then reset the
CPU to the A30 conservative Auto policy after startup.

The comparison build removed `USE_BLARGG_APU=1`, selecting Snes9x 2005's
default fast APU, and first ran at the fixed Performance CPU policy. The
hardware tester described the result as night-and-day better and seemingly
perfect: full-speed, responsive gameplay without the prior visible tearing.
A final isolation run used that same fast-APU core with the normal Auto CPU
policy. The tester could not discern a difference from the Performance run.

The platform therefore ships plain Snes9x 2005, does not force the Blargg APU,
and retains automatic CPU scaling for SFC. Since the tearing disappeared when
the core workload fell while the presentation path remained unchanged, the
observed tearing was a missed-frame-deadline symptom rather than evidence that
the A30 presentation shim needs a separate swap-pacing change.

The native FCEUmm core was next launched with zipped 1942. The hardware tester
reported good performance, working face buttons, and working analog-to-D-pad
input with no observed functional issues. The audio sounded somewhat unusual,
but the tester had not played this version of 1942 before, so this is recorded
as inconclusive rather than an audio defect. A familiar reference title should
be used if NES audio fidelity needs closer evaluation.

The native PicoDrive core was launched with zipped Sonic the Hedgehog 2. It
reported a 320x240 base geometry, switched to the title's 320x224 active frame,
and ran at 60 Hz with RGB565 output. Performance and all exercised controls
were good. The tester observed a narrow strip of mismatched level pixels along
the physical bottom edge.

The save-state preview captured the same defect before final presentation: a
small number of doubled source columns at the logical frame's left edge. The
A30's counter-clockwise presentation rotation maps that logical edge to the
physical bottom. This rules out the A30 rotation/FBO shim and points instead
to PicoDrive border/overscan output or upstream frame content. The tester then
reproduced the identical strip with the same title under Spruce and on a
TrimUI Brick. PicoDrive therefore passes the my282 hardware gate; no
platform-specific crop is applied.

The native Gambatte core—not the Spruce binary used during the initial
MinArch proof—was then staged and launched with zipped Tetris. The hardware
tester reported gameplay, audio, presentation, and exercised controls all
good. This closes native-core validation for GB/GBC.

Five of the six initial native cores have now been exercised on the A30:
FCEUmm, Gambatte, gpSP, PicoDrive, and Snes9x 2005. PCSX-ReARMed remains
runtime-untested only because `/mnt/SDCARD/Roms/PS` contains no game image.

## Standalone package preparation

The package initially produced a 29 MB pre-expanded card tree with the stock A30
`.tmp_update/updater` hook, a `sun8i`/`/usr/miyoo` dispatcher, the my282 boot
supervisor, and `miyoo/app/MainUI` plus no-op `keymon` fallback entry points.
It includes the shared NextUI resource tree, a production frontend/game
supervisor, seven native emulator paks, and the six audited native cores.

The Spruce test harness placed `/mnt/SDCARD/miyoo/lib` ahead of stock
libraries, so successful harness runs did not prove standalone SDL
independence. An attempted self-contained run exposed that the published A30
toolchain's SDL2 is a generic X11 build, despite the SDK also carrying the
Mali EGL libraries. The frontend stayed blank and logged a null renderer plus
`Failed to create temporary texture: Parameter 'renderer' is invalid`.

Replacing only SDL2, SDL2_image, and SDL2_ttf with the exact A30 runtime
versions used by the successful earlier tests fixed the run. The log reported
`MALI_CreateWindow`, the `opengles2` renderer, a 640x480 output, and successful
frontend initialization. The hardware tester confirmed that the menu appeared
and looked correct throughout the bounded run. MinUI's current `my282` package
likewise ships no private SDL2 and relies on the firmware ABI.

The package therefore must not install the generic SDK SDL libraries. It uses
the Mali-enabled SDL implementation supplied under `/usr/miyoo/lib` by the A30
firmware, while continuing to package NextUI-specific dependencies such as
libsamplerate, LZ4, and libzip. A true cold-boot run without Spruce's
`/mnt/SDCARD/miyoo/lib` bind mount remains the next gate before replacing the
card's boot hook.

A follow-up test moved all three temporary SDL libraries out of
`.system/my282/lib` and ran the same recovery-wrapped frontend. It again logged
`MALI_CreateWindow`, selected `opengles2`, initialized the 640x480 frontend,
and returned cleanly to Spruce. This validates the package library ordering
and its deliberate firmware-SDL dependency. It does not yet distinguish
Spruce's SD-card bind mount from the underlying `/usr/miyoo/lib`, which
requires the cold-boot test.

The top-level my282 build now drives libmsettings, NextUI, MinArch, core
availability, and final card staging. The toolchain runner mounts the shared
release skeleton read-only, so a clean package build no longer depends on
stale assets left in the stage directory.

## Standalone cold-boot follow-up

The tester copied the package to a separate SD card and booted directly into
NextUI. This validates the update dispatcher, boot supervisor, frontend
launcher, firmware `/usr/miyoo/lib` dependency, and absence of Spruce runtime
requirements. FC, GB/GBC, GBA, MD, and SFC games all launched and worked.

The first standalone package exposed two omitted services. Physical volume
buttons did not alter game volume or trigger the adjustment indicator.
Menu+Volume displayed the brightness/volume UI but did not change its value.
This matches NextUI's architecture: `PWR_update` displays shared settings,
while `keymon.elf` normally changes them. The package suppressed stock keymon
without supplying an A30 replacement.

The corrected 30 MB tree adds a native A30 key monitor for Volume +/- and
Menu+Volume brightness, starts it across frontend and game sessions, and
persists changes through `libmsettings`. It also builds and packages NextUI's
Settings application under `Tools/my282/Settings.pak`. Both additions compile
and have complete static dependency closure but await standalone hardware
validation.

A PS1 image was attempted but did not visibly launch. PCSX-ReARMed remains
ABI-audited but runtime-unconfirmed until the card's
`.userdata/my282/logs/PS.txt` is inspected.

The subsequent `.userdata` capture showed that the standalone FAT filesystem
was mounted read-only. `nextui.txt` contained repeated `Read-only file system`
errors for both msettings and frontend configuration, keymon could not persist
its settings, and `PS.txt` was zero bytes. Because the shell must open the PS
log redirection before executing MinArch, that zero-byte/read-only result does
not yet demonstrate a PCSX-ReARMed failure.

The shutdown implementation at that point called BusyBox `poweroff` while the
SD card remained mounted. Spruce's A30 shutdown uses a second-stage script
copied to `/tmp` specifically so it can sync and unmount the card before
poweroff. The package now follows that essential sequence and attempts a
read/write remount at boot if stock firmware mounted an unclean FAT volume
read-only.

The same follow-up confirmed working standalone brightness and generally
working volume adjustment. Color temperature is unsupported by the current
A30 hardware layer and is now removed from the my282 shortcut/capability set.
Volume writes now use ALSA's mixer API directly rather than spawning `amixer`,
which the stock-only logs reported as failing.

Settings now initializes absent firmware-version text before constructing
About, provides a safe timezone fallback for stock images without zoneinfo,
identifies the A30 explicitly, and writes its own diagnostic log under
`.userdata/my282/logs/settings.txt`. MinArch also uses unbuffered startup logs
and exits cleanly on a failed core load so the next PS test will be
diagnostic.

A second, newly formatted SD card reproduced the read-only mount, theme write
failures, empty `PS.txt`, About crash, and inability to reopen Settings after
the PS attempt. Its `nextui.txt` again explicitly reported `Read-only file
system`. This rules out one bad card and exposed two launcher defects. The
boot remount used only the mountpoint, but the A30's BusyBox mount requires the
block device and mountpoint. In addition, mandatory shell log redirections
prevented PS MinArch, Settings, and even the restarted frontend from executing
when the log could not be opened. The next package resolves the block device
from `/proc/mounts`, falls back to `/tmp` logs whenever SD logging is
unavailable, and remounts read-only before final unmount at shutdown instead
of using a lazy unmount. PSX core execution is therefore still untested.

The direct framebuffer clear did not suppress the brief unrotated frame on
Mali window destruction. The next package uses `FBIOBLANK` to keep scanout
blank from window teardown until the first correctly oriented presentation by
the next process. About value getters now emit unbuffered trace points so any
remaining crash can be localized precisely.

After formatting with Rufus, the package booted writable and PCSX-ReARMed
successfully ran an extracted BIN/CUE image at 60 FPS using its ARMv7 NEON
renderer and dynarec. PCSX advertises `need_fullpath: 1`; MinArch therefore
block-extracts a ZIP to temporary storage before launch. The initial ZIP test
was manually aborted during this long, indicator-free extraction, so archive
support is slow rather than broken. Extracted BIN/CUE, CHD, or PBP is preferred
for PS1.

This run exposed shared platform defects. ALSA found `Soft Volume Master`, but
the simple-mixer API rejected every write with `Operation not permitted`.
That control is an ALSA user control rather than a conventional playback
simple element; the next package uses the direct control-element API, matching
Spruce's effective `amixer set` behavior. PS defaulted to DualShock and thus
sent the A30 stick only as true analog input; it now defaults to Standard so
the stick mirrors the D-pad, with DualShock still selectable per game.

A fixed vertical tear boundary was visible across PS1, GBA, and GBC, showing
that it belongs to the rotated Mali presentation rather than a core. The next
package enables the EGL swap interval and waits on framebuffer vsync before
both renderer and GLES swaps. Since framebuffer blanking alone still did not
hide the unrotated teardown frame, the A30 path now keeps GPU/window objects
alive until immediate process exit instead of dismantling them visibly.

Hardware validation confirmed that the vsync changes removed the fixed tear
boundary without regressing performance. The very brief vertically flipped
frame on game exit remains. Because deferring MinArch's renderer, context, and
window teardown did not remove it, the remaining artifact is most likely at
the process handoff or the frontend's first Mali frame rather than in the
emulator renderer itself.

The refreshed standalone logs explain the remaining intermittent volume
failure. Keymon receives every button adjustment, but direct writes to `Soft
Volume Master` fail with `EPERM` while another process owns the ALSA softvol
control (and can initially fail with `ENOENT` before the PCM creates it).
Allium's A30 implementation instead uses the codec's `headphone volume`
control, a writable hardware element with range 0-63 that drives both speaker
and jack. The next build uses that hardware control and retains NextUI's 21
logical volume steps.

Wi-Fi and development SSH are now part of the my282 package for live hardware
diagnostics. The existing NextUI Wi-Fi menu uses an A30-specific RTL8188FU,
`wpa_supplicant`, and BusyBox `udhcpc` lifecycle script, with credentials kept
under `.userdata/my282/wifi`. `Tools > SSH` toggles an A30-tested Dropbear
2025.88 service after Wi-Fi has an address; its state and log are kept under
`.userdata/my282/ssh` and `.userdata/my282/logs/ssh.txt`. Shutdown explicitly
stops the network processes and releases SSH's temporary `/etc/passwd` bind
mount before unmounting the SD card.

The apparently instantaneous shutdown display is currently explained by
`PLAT_powerOff()` muting audio and switching off the backlight before the
frontend exits. The safe shutdown stage then continues invisibly from `/tmp`.
SSH will be used to timestamp and verify that stage before changing the visual
sequence merely to make it look slower.

Live SSH diagnostics at `192.168.0.166` validated the standalone network and
audio paths. The A30 associated through NextUI's Wi-Fi UI, obtained DHCP, and
reported its SSID, address, signal strength, and 72 Mbps link through the
generic backend. Dropbear 2025.88 accepted the packaged `spruce` account after
restoring its firmware-valid `/bin/ash` login shell; `/bin/sh` was rejected by
Dropbear's `/etc/shells` validation.

During a live MinArch session, repeated physical volume adjustments changed
the codec control from 43 to 50, 40, and 37 while the game retained ALSA. The
keymon log remained free of write errors. This validates `headphone volume` as
the correct shared hardware control and closes the intermittent softvol
ownership failure.

About itself was also validated: every displayed value getter completed while
the tester navigated the page. The trailing `terminate called without an
active exception` occurred only when exiting Settings. Settings had left its
Wi-Fi `std::thread` without explicit top-level ownership. The next binary owns
the Wi-Fi/Bluetooth menus with `unique_ptr`, stops their workers through atomic
flags, and joins them before graphics and settings teardown.

The next my282-only presentation test carries raw backlight state through
`/tmp/nextui-backlight`. It dims the physical panel across Mali-fbdev window
creation/destruction and restores the prior raw level only after the first
correctly rotated frame. This targets the remaining process-handoff flip
without changing `common/generic_video.c` or persisting extra settings writes.

The first early-exit blackout suppressed the flip but also hid MinArch's normal
fade. Moving the blackout after the fade exposed that the fade screenshot
itself was inverted. A TrimUI Brick comparison confirmed the important display
difference: the Brick is landscape-native, whereas the A30 renders into a
logical 640x480 FBO before rotating into its portrait scanout. The generic GL
screenshot row flip is correct for the Brick but redundant on the A30. The
final A30-local capture reads the logical FBO without that extra flip, then
latches the backlight after the fade until the frontend presents. Hardware
testing reported the complete game-exit transition as correct.

Settings teardown is also resolved. Explicit Wi-Fi/Bluetooth menu ownership
and cooperative battery-monitor shutdown removed the trailing
`terminate called without an active exception`; the log now reaches network,
menu, settings, power, input, Bluetooth, and video cleanup in order. A short
visible pause can remain when exit catches an active `wpa_cli` scan. Upstream
Settings scans whenever the application is open and Wi-Fi is enabled, even if
the Wi-Fi submenu is hidden. This is logged as deferred polish rather than an
A30 blocker because teardown is clean and the worker stops with Settings.
